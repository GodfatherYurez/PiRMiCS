# Отчет о выполнении практической работы №2

## 1. Тема и цель работы

Тема работы: измерение задержки обмена UDP-пакетами.

Цель работы - дополнить UDP-взаимодействие из ПР1 измерением времени кругового пути пакета, обработкой тайм-аутов и сбором данных о задержке, джиттере и потерях.

В рамках работы реализован консольный прототип на C# и .NET 8. Клиент отправляет пакеты `PING`, сервер возвращает `PONG`, а клиент сохраняет результаты измерений в CSV-файл. ПР2 расположена в отдельном каталоге `PR2` и не изменяет исходные файлы первой практической работы.

## 2. Выбор технологии

Для реализации выбран язык C# и платформа .NET 8. Для UDP-обмена используется `UdpClient` из пространства имен `System.Net.Sockets`. Для измерения интервалов применяется монотонный таймер `Stopwatch`.

Выбор C# обусловлен следующими причинами:

- язык и платформа использовались в ПР1;
- `UdpClient` позволяет работать с UDP без ручного управления системными сокетами;
- `Stopwatch` подходит для измерения коротких временных интервалов;
- .NET содержит средства сериализации байтов, отмены операций и работы с сетевыми адресами;
- проект собирается и запускается на Windows при установленном .NET SDK.

Внешние библиотеки и дополнительные NuGet-зависимости не используются.

## 3. Схема измерения

Для эксперимента используется схема «клиент - сервер». Клиент отправляет серверу `PING` с номером последовательности и временем отправки. Сервер принимает пакет и возвращает `PONG` с тем же номером. После получения `PONG` клиент вычисляет RTT по собственным часам.

```text
Клиент  ---> PING --->  UDP-сервер
Клиент  <--- PONG <---  UDP-сервер
```

RTT рассчитывается по формуле:

```text
RTT = время получения PONG клиентом - время отправки PING клиентом
```

Серверные временные метки записываются в `PONG` для диагностики. В расчете RTT они не участвуют, поэтому синхронизация часов на разных компьютерах не требуется.

## 4. Общая структура проекта

Проект состоит из следующих частей:

- `Protocol` - описание пакетов `PING` и `PONG`, их сериализация и проверка;
- `Telemetry` - хранение ожидаемых ответов, расчет RTT, SRTT и джиттера;
- `Transport` - небольшая обертка над UDP;
- `Server` - прием `PING`, эмуляция условий сети и отправка `PONG`;
- `Client` - отправка запросов, прием ответов и сохранение CSV;
- `Tests` - автоматическая проверка протокола и метрик;
- `docs` - конфигурация экспериментов, исходные измерения и документация.

## 5. Реализованный UDP-протокол

Каждая UDP-датаграмма содержит один пакет. Все многобайтовые значения передаются в сетевом порядке байтов `big-endian`. Заголовок занимает 9 байт.

| Поле | Размер | Назначение |
|---|---:|---|
| Magic | 2 байта | сигнатура протокола `0x4D50` |
| PacketType | 1 байт | тип пакета: `PING` или `PONG` |
| SequenceNumber | 2 байта | порядковый номер пакета |
| PayloadSize | 2 байта | размер полезной нагрузки |
| ProtocolVersion | 2 байта | версия протокола |

Пакет `PING` содержит время отправки клиента. Пакет `PONG` содержит исходную метку времени клиента, а также время приема и отправки на сервере.

Перед чтением полезной нагрузки программа проверяет размер заголовка, сигнатуру, версию, тип пакета, размер полезной нагрузки и границы буфера. Неверные пакеты отбрасываются без аварийного завершения программы.

## 6. Реализованная логика обмена

Клиент присваивает каждому `PING` уникальный `SequenceNumber`, сохраняет время отправки и ожидает `PONG` не более 1000 мс. После ответа клиент выводит результат в консоль и сохраняет строку в CSV-файл.

Сервер выполняет следующие действия:

- принимает UDP-датаграмму;
- проверяет формат пакета;
- отбрасывает пакет с вероятностью, заданной параметром `loss_rate`;
- добавляет фиксированную задержку и случайный джиттер;
- формирует `PONG` с тем же номером последовательности;
- отправляет ответ клиенту;
- выводит сведения о пакете в консольный журнал.

Параметры сервера имеют вид: `port delay_ms jitter_min_ms jitter_max_ms loss_rate seed`. Это позволяет воспроизводимо запускать серии без задержки, с фиксированной задержкой, с джиттером, с потерями и в комбинированном режиме.

## 7. Измеряемые показатели

Для каждого запроса программа фиксирует один из следующих статусов:

- `received` - ответ получен не позднее чем через 1000 мс;
- `timeout` - ответ не получен за 1000 мс;
- `late_response` - ответ получен после тайм-аута;
- `duplicate_response` - получен повторный ответ с тем же номером;
- `unknown_response` - получен ответ для неизвестного номера.

Сглаженная задержка `SRTT` после первого измерения равна RTT. Для следующих ответов применяется формула:

```text
SRTT = 0.875 * SRTT + 0.125 * RTT
```

Джиттер вычисляется как среднее значение `|RTT_i - RTT_(i-1)|` для соседних успешных ответов. Доля потерь вычисляется как `timeouts / sent * 100%`. Повторная отправка пакетов в этой версии не выполняется.

## 8. Ограничения текущего прототипа

Текущая версия предназначена для измерения UDP-обмена и не является полноценной системой надежной доставки данных. В ней пока отсутствуют:

- повторная отправка потерянных пакетов;
- подтверждение доставки;
- упорядочивание пакетов;
- защита от повторов на уровне приложения;
- измерения между разными компьютерами и через реальную внешнюю сеть;
- автоматическое построение графиков по CSV;
- шифрование и авторизация.

Выполненный baseline-прогон использует адрес `127.0.0.1`, поэтому пакеты не проходят через физическую сеть. Его значения подходят для проверки программы, но не отражают задержку соединения между разными устройствами.

## 9. Проверка результата

Проект собирается и проверяется командами:

```powershell
dotnet build Protocol/Protocol.csproj -c Release
dotnet build Telemetry/Telemetry.csproj -c Release
dotnet build Transport/Transport.csproj -c Release
dotnet build Server/Server.csproj -c Release
dotnet build Client/Client.csproj -c Release
dotnet run --project Tests/Tests.csproj -c Release
```

Для локальной проверки сервер запускается в первом терминале:

```powershell
dotnet Server/bin/Release/net8.0/Server.dll 7777 0 0 0 0 20260914
```

Во втором терминале запускается клиент:

```powershell
dotnet Client/bin/Release/net8.0/Client.dll 127.0.0.1 7777 baseline 3 200 docs/latency_samples.csv
```

В сохраненном файле [latency_samples.csv](latency_samples.csv) находятся три успешных измерения baseline-серии.

| № | RTT, мс | SRTT, мс | Статус |
|---:|---:|---:|---|
| 1 | 0,900 | 0,900 | `received` |
| 2 | 0,800 | 0,888 | `received` |
| 3 | 1,100 | 0,915 | `received` |

Средний RTT составил 0,933 мс. Минимальное значение равно 0,800 мс, максимальное - 1,100 мс. Средний джиттер составил 0,250 мс. Тайм-аутов не зафиксировано, поэтому доля потерь равна 0%.

Автоматические тесты дополнительно проверяют сериализацию `PING` и `PONG`, отклонение поврежденных пакетов, расчет RTT, SRTT и джиттера, а также обработку тайм-аута, позднего, дублирующегося и неизвестного ответа.

## 10. Итог

В результате создана программа для измерения задержки UDP-обмена. Она реализует пакеты `PING` и `PONG`, проверяет входящие датаграммы, измеряет RTT, рассчитывает SRTT и джиттер, фиксирует тайм-ауты и сохраняет результаты в CSV.

Baseline-прогон на `127.0.0.1` показал RTT от 0,800 до 1,100 мс без потерь. Для дальнейшего исследования можно выполнить серии с фиксированной задержкой, джиттером и потерями по параметрам из [Experiment_Config.md](Experiment_Config.md), а затем построить графики по полученным CSV-файлам.
