# Отчёт по практической работе 2

## Тема и цель работы

Тема работы: измерение задержки обмена UDP-пакетами. Цель работы — реализовать обмен `PING`/`PONG`, измерять время кругового пути пакета (RTT), фиксировать потери и оценивать изменение задержки между сообщениями.

Практическая работа продолжает ПР1. Исходные файлы ПР1 не изменялись: реализация измерений находится в каталоге `PR2`.

## Состав программы

Клиент отправляет серверу пакет `PING`. В пакете передаются порядковый номер и отметка времени клиента. Сервер принимает пакет и отправляет `PONG` с тем же номером. Клиент по своему монотонному таймеру `Stopwatch` вычисляет RTT:

```text
RTT = время получения PONG клиентом − время отправки PING клиентом
```

В UDP-пакете передаются поля `Magic`, тип пакета, номер последовательности, размер полезной нагрузки и версия протокола. Числа сериализуются в порядке `big-endian`. Перед обработкой программа проверяет размер пакета, сигнатуру, версию, тип и размер полезной нагрузки. Некорректные датаграммы отбрасываются.

Сервер принимает параметры командной строки и может искусственно создать фиксированную задержку, джиттер или потерю пакета. Это позволяет проводить одинаковые эксперименты без внешнего сетевого эмулятора.

## Измеряемые показатели

Для каждого отправленного `PING` клиент сохраняет запись в таблице ожидаемых ответов. Возможны следующие статусы:

| Статус | Значение |
|---|---|
| `received` | Ответ получен не позднее чем через 1000 мс. |
| `timeout` | Ответ не получен за 1000 мс. |
| `late_response` | Ответ получен после тайм-аута. |
| `duplicate_response` | Получен повторный ответ с тем же номером. |
| `unknown_response` | Получен ответ для неизвестного номера. |

Дополнительно вычисляются:

- `SRTT` — сглаженная оценка RTT. После первого измерения она равна RTT; далее применяется формула `SRTT = 0,875 × SRTT + 0,125 × RTT`.
- Джиттер — среднее значение `|RTT_i − RTT_(i−1)|` для соседних успешных ответов.
- Доля потерь — `timeouts / sent × 100%`.

Повторная отправка пакетов в ПР2 не выполняется.

## Условия эксперимента

Измерение выполнено на loopback-интерфейсе `127.0.0.1:7777` с помощью `UdpClient`. Сервер и клиент запускались на одном компьютере под Windows 11 x64; проект собран для `net8.0`. Тайм-аут клиента — 1000 мс.

В baseline-серии сервер запущен без искусственной задержки, джиттера и потерь:

```powershell
dotnet Server/bin/Release/net8.0/Server.dll 7777 0 0 0 0 20260914
```

Клиент запускался с идентификатором эксперимента `baseline`; исходные значения записаны в файл [latency_samples.csv](latency_samples.csv).

## Результаты baseline-прогона

В сохранённом CSV находятся три успешных измерения. Результаты приведены в таблице.

| № | RTT, мс | SRTT, мс | Статус |
|---:|---:|---:|---|
| 1 | 0,900 | 0,900 | `received` |
| 2 | 0,800 | 0,888 | `received` |
| 3 | 1,100 | 0,915 | `received` |

Средний RTT составил 0,933 мс. Минимальное значение — 0,800 мс, максимальное — 1,100 мс. Средний джиттер между соседними ответами составил 0,250 мс. Тайм-аутов не зафиксировано, поэтому доля потерь в этой серии равна 0%.

Небольшой RTT ожидаем для loopback-соединения: пакеты не проходят через физическую сеть. Разброс значений связан с планированием потоков ОС, работой таймера и другими локальными процессами.

## Проверка реализации

Автоматические тесты проверяют:

- сериализацию и обратное чтение пакетов `PING` и `PONG`;
- отклонение усечённого пакета, неверной версии и неверного размера полезной нагрузки;
- расчёт RTT, SRTT и джиттера;
- обработку тайм-аута, позднего, дублирующегося и неизвестного ответа.

Тесты запускаются командой:

```powershell
dotnet run --project Tests/Tests.csproj -c Release
```

## Вывод

В ПР2 реализован измерительный UDP-клиент и серверный ответ `PING`/`PONG`. Программа проверяет формат входящих пакетов, измеряет RTT, считает сглаженную задержку и джиттер, а также различает потери и нестандартные ответы. Baseline-прогон на `127.0.0.1` показал RTT от 0,800 до 1,100 мс без потерь.

Для сравнения режимов с задержкой, джиттером и потерями нужно выполнить отдельные серии из [Experiment_Config.md](Experiment_Config.md) и сохранить каждую в отдельный CSV-файл. До выполнения таких серий в отчёте не следует указывать их численные результаты.
